# Implementation Principles

## 핵심 원칙

- 모든 코드는 경계와 기능을 기반으로 작성해 중복을 최소화한다.
- 함수, 변수, 클래스, 컴포넌트 이름은 실제 책임을 드러내야 한다.
- 입출력은 명확해야 하며 내부 구현을 읽지 않아도 결과를 예측할 수 있어야 한다.
- 함수/클래스/모듈은 참조 가능한 설명 문서를 가져야 한다.
- 책임 경계를 흐리는 편의 구현은 금지한다.
- 모든 기능은 의존성 주입을 기본으로 설계한다.
- 전역 변수와 mutable singleton은 만들지 않는 것을 원칙으로 한다.
- Factory, Adapter, Strategy, Repository, Unit of Work, State Machine 같은 패턴은 경계를 명확히 하거나 구현체 교체가 필요한 경우 적극적으로 사용한다.
- 단순성을 해치는 과잉 추상화는 금지한다.

## 기능 분해 기준

- 기능은 화면이 아니라 책임, 입력, 출력, 저장 데이터, 실패 상태를 기준으로 나눈다.
- 기능 간 직접 참조 대신 명시적인 contract와 service interface를 둔다.
- 한 기능의 내부 상태를 다른 기능이 직접 수정하지 않는다.
- 기능별 구현 폴더에는 README를 두고 공개 API와 의존성을 기록한다.

## Mock / Fallback 금지선

- 프론트만 설계될 때 mock 데이터는 코드와 분리해 작성한다.
- 화면, 훅, 컴포넌트 내부에 mock 데이터를 섞지 않는다.
- mock은 `src/api` 뒤의 API 계약 대체 구현체로만 둔다.
- 명시적으로 지시되지 않은 폴백은 만들지 않는다.
- 백엔드가 제공하지 않은 데이터를 프론트에서 생성하지 않는다.
- 백엔드 구현 시에도 실패를 성공처럼 감추는 폴백, 빈 데이터로 덮는 폴백, 의미 없는 기본값 주입은 금지한다.

## 문서화 기준

- 기능, API 계약, 폴더/파일 책임, 모듈 경계가 바뀌면 관련 MD 문서를 함께 갱신한다.
- 함수/클래스 설명은 구현 세부가 아니라 책임, 입력, 출력, 부작용, 실패 조건을 중심으로 작성한다.
- 하드닝된 모듈은 문서화된 계약을 기준으로 참조하며, 수정이 꼭 필요하면 사용자 허가를 먼저 받는다.
- factory/adapter/strategy/repository를 추가하면 interface, 구현체, 생성 위치, 주입 의존성, 실패 처리 방식을 문서화한다.

## 에러 처리 기준

- 이미지 누락, API 실패, 모델 실패, 권한 부족, 계약 누락은 사용자에게 명확히 드러낸다.
- 실패 상태를 합격/불합격으로 변환하지 않는다.
- retry가 필요하면 retry 상태와 원인을 저장하거나 표시한다.
- 사용자 업무를 계속 진행시키기 위한 임시 성공 상태를 만들지 않는다.

## 향후 백엔드 참고

- DB 접근 구조는 향후 백엔드 구현 시 기존 이도 프로젝트의 `PGDBManager`류 패턴을 참고한다.
- 단, SANIL의 DB 계약과 모듈 경계에 맞게 재문서화하고 그대로 복사하지 않는다.
