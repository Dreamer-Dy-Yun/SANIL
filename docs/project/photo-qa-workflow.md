# Photo QA Workflow

## 목표

기준 대조군 사진과 QA 대상 사진을 비교해 제품별 QA 합부 판단을 보조한다.

## 기준 사진 등록

1. 제품을 선택하거나 등록한다.
2. 확인 개소별 기준 사진을 촬영/업로드한다.
3. 각 기준 사진은 제품 내 촬영 순서와 촬영 의도를 가진다.
4. 기준 사진에서 촬영 가이드에 사용할 외곽선 또는 정렬 기준을 추출한다.
5. 기준 사진별 주의사항은 VLM/LLM 비교 프롬프트에 포함할 수 있다.

관련 DB 설계:

- `PRODUCT`: 제품 정보
- `REFERENCE`: 제품별 대조군 사진과 촬영 순서
- `IMAGE`: 저장 이미지 메타데이터
- `PROMPT`: 공통 프롬프트

## QA 대상 촬영

1. 제품을 선택한다.
2. 기준 사진 순서에 따라 QA 대상 촬영 화면을 제공한다.
3. 화면에는 기준 사진에서 얻은 외곽선/가이드라인을 오버레이한다.
4. 사용자는 가이드라인에 맞춰 QA 대상 사진을 촬영한다.
5. 모든 필수 촬영이 끝나야 최종 결과 화면으로 이동한다.

## VLM/LLM 처리 전략

권장 전략은 "촬영 직후 백그라운드 개별 처리 + 전체 촬영 완료 후 최종 집계"다.

근거:

- 촬영 사이의 대기 시간을 활용해 최종 결과 대기 시간을 줄일 수 있다.
- 개별 이미지 처리 실패를 마지막 화면 진입 전에 재시도하거나 명확히 실패로 표시할 수 있다.
- 사용자는 모든 촬영을 끝내기 전까지 부분 합부 결과를 보지 않으므로 업무 흐름이 흔들리지 않는다.
- 최종 판정은 모든 기준/대상 쌍이 처리된 뒤 한 번에 집계할 수 있다.

단, 하나의 프롬프트가 모든 이미지의 문맥을 동시에 필요로 하는 모델/업무 조건이면 전체 촬영 후 일괄 요청으로 바꿀 수 있다. 이 경우에도 사용자가 일부 결과를 먼저 보는 UI는 만들지 않는다.

## 결과 표시

- 결과는 모든 촬영이 끝난 뒤 표시한다.
- 결과는 검사 단위의 최종 상태와 촬영 개소별 비교 근거를 함께 제공한다.
- 모델 응답 실패, 이미지 누락, 필수 계약 누락은 합격/불합격으로 위장하지 않는다.

관련 DB 설계:

- `INSPECTED`: 대상 이미지 검사 이력 및 판정 결과
- `LLM`: LLM API 설정
- `LLM_USAGE`: LLM 사용 로그

주의:

- 최신 DB 설계에는 `INSPECTION_SESSION` 테이블이 추가되어 전체 촬영 묶음을 표현할 수 있다.
- API에서는 `INSPECTION_SESSION.uuid`를 `inspectionSessionUuid`로 노출한다.
- 별도 세션 테이블은 1차 구현 필수 조건이 아니며, 세션 메타데이터가 늘어날 때 후속 확장으로 검토한다.

## 상태 모델 초안

| 상태 | 의미 |
|---|---|
| `capture_required` | 촬영이 필요한 기준 사진이 남아 있음 |
| `captured` | QA 대상 사진이 저장됨 |
| `queued` | VLM/LLM 처리를 대기 중 |
| `processing` | VLM/LLM 처리 중 |
| `processed` | 개별 비교 결과가 저장됨 |
| `failed` | 처리 실패, 재시도 또는 사용자 확인 필요 |
| `ready_to_review` | 모든 촬영과 처리가 끝나 최종 결과 표시 가능 |

이 상태명은 프론트 구현 전 초안이며, 백엔드 API 계약 확정 시 enum/check constraint와 함께 재검토한다.
